# Hamsters Life — работа разными агентами

Как вести разработку командой ИИ-агентов (Claude Code и подобные) под присмотром человека: кто за что отвечает, как делить задачи и в каком порядке их брать.

## 1. Принципы

1. **Владение по пакетам.** У каждого пакета/приложения один агент-владелец. Чужой пакет правится только через задачу его владельцу или с явного согласия координатора.
2. **Сначала контракт, потом реализация.** Интерфейсы (`IGameView`, `ISimSource`, типы `protocol`, схемы `content`) фиксируются отдельной задачей до параллельной работы. Изменение контракта — отдельная задача с ревью всех потребителей.
3. **Логика отдельно от UI.** Расчёт живёт в `core`/`levelgen`/`ai`; агент UI не пишет правил, агент `core` не импортирует Pixi/DOM. Проверка: можно ли протестировать без окна?
4. **Одна задача — одна ветка — один PR.** Небольшие PR (до ~400 строк изменений), каждый с тестами.
5. **Детерминизм и безопасность не откладываются.** Любой PR в `core` проходит тест детерминизма; любой PR в `game-server`/`api` — тесты безопасности.
6. **Человек принимает решения о цели** (дизайн, баланс-ощущения, визуальный стиль, релиз), агенты — о реализации.

## 2. Роли

| Роль | Владеет | Делает | Не делает |
|---|---|---|---|
| **Координатор (архитектор)** | `docs/`, корневые конфиги, контракты | режет этапы на задачи, ведёт доску, утверждает изменения контрактов, разрешает конфликты, проверяет критерии этапа | не пишет фичи сам |
| **Агент ядра (Core)** | `packages/core`, `packages/content` (схемы) | правила, бой, производство, бусты, рода войск, магия, фиксированная арифметика, `ProtectedInt` | не трогает рендер и сеть |
| **Агент контента и баланса** | `packages/content` (данные), `tools/balance-sim` | числа баланса, прогон симулятора, отчёты о винрейтах | не меняет формулы в `core` (просит Core) |
| **Агент генератора** | `packages/levelgen` | формы карт, симметрия, проверка симуляциями, оценка сложности | |
| **Агент ИИ** | `packages/ai` | боты пяти уровней, характеры, поведение боссов | не читает скрытое состояние сверх правил уровня |
| **Агент рендера** | `apps/client/src/render` | Pixi-сцена, шейдеры, частицы, интерполяция, бюджет кадра | не решает игровые исходы |
| **Агент интерфейса** | `apps/client/src/ui`, `input`, презентеры | меню, HUD, настройки, комната трофеев, жесты → команды, `GamePresenter` | не пишет правила игры |
| **Агент сети** | `packages/protocol`, `apps/game-server`, `apps/client/src/net` | комнаты, подбор, дельты, переподключение, проверка команд, античит | |
| **Агент бэкенда** | `apps/api`, `infra/` (БД, миграции) | аккаунты, сессии, профиль, трофеи, рейтинг, шифрование полей | |
| **Агент безопасности (ревьюер)** | `docs/SECURITY.md`, тесты безопасности | ревью всех PR в `protocol`, `game-server`, `api`, `net`; злые тесты; аудит зависимостей | не пишет фичи |
| **Агент QA** | `e2e/`, смоуки производительности | сквозные сценарии Playwright, тест детерминизма, регрессии, бюджет FPS | |
| **Агент арта и звука** | `apps/client/assets`, `tools/assets` | атласы, промпты/заказы ассетов, сжатие, звуковые спрайты | |

На ранних этапах роли совмещаются: этап 0–1 тянут 3–4 агента (Координатор, Core+Content, Render+UI, QA).

## 3. Карточка задачи

Каждая задача на доске (GitHub Issues/Projects) оформляется так:

```
Название: [core] Одновременное прибытие отрядов нескольких врагов
Этап: 1        Владелец: Core       Зависит от: #12 (формула боя)
Контекст: IDEA.md §3.4
Что сделать: ...
Контракт: какие публичные типы меняются (нет / список)
Критерии приёмки:
  - тесты: ... (имена)
  - тест детерминизма зелёный
  - нет импортов dom/pixi в core
Вне объёма: ...
```

Агент начинает работу, только если у задачи есть критерии приёмки и закрыты зависимости.

## 4. Порядок работы

### 4.1 Цикл одной задачи
1. Агент берёт задачу, создаёт ветку `<роль>/<номер>-<кратко>`.
2. Читает указанные разделы `docs/`, не весь репозиторий.
3. Пишет тесты → реализацию → прогоняет **только тесты затронутых пакетов** (`pnpm --filter core test`); полный набор — в CI.
4. Открывает PR с описанием: что сделано, как проверено, что не сделано.
5. Ревью: владелец соседнего пакета-потребителя + агент безопасности (для сетевых/серверных PR) + человек для дизайна и визуала.
6. После слияния — отметка в карточке, сообщение задачам, которые ждали этой.

### 4.2 Порядок внутри этапа
1. **Координатор**: разбивает этап, пишет/обновляет контракты (одна задача, сливается первой).
2. **Параллельно** по зафиксированным контрактам: Core, Render, UI, (Net/Backend — с этапа 7).
3. **Интеграция**: UI-агент соединяет презентер с реальным `core`, QA пишет сквозной сценарий.
4. **Баланс и полировка**: агент контента прогоняет симулятор, рендер — бюджет кадра.
5. **Приёмка этапа**: координатор проходит критерии из ROADMAP.md, человек играет сборку.

### 4.3 Пример: этап 1 по дорожкам

| Дорожка | Задачи по порядку |
|---|---|
| Координатор | контракты `GameState`, `Command`, `IGameView`, `ISimSource` → приёмка |
| Core | состояние и тик → производство → полёт → бой и захват → бусты → повтор/хэш → `ProtectedInt` |
| Content | схемы планет/бустов → стартовые карты JSON |
| AI | бот «Боец» (после боя и бустов в core) |
| Render | фон и планеты → отряды и стрелка → эффекты захвата и бустов → интерполяция |
| UI | меню и выбор матча → жест стрелки и доли → HUD бустов → экран итогов → Worker-источник |
| QA | тест детерминизма в CI → сквозной «матч с ботом» → смоук FPS |

## 5. Правила совместной работы

- **Конфликты файлов:** два агента не правят один файл одновременно. Если задача требует правки в чужом пакете — она делится на две.
- **Общие файлы** (`package.json` корня, конфиги CI, `protocol`) меняются только через координатора или владельца.
- **Передача контекста:** итог задачи пишется в PR и, если это долговременное решение, — в `docs/` (раздел «Решения» в ARCHITECTURE.md). Агент без общей памяти должен понять решение из документов.
- **Блокировка:** застрявший агент пишет в карточку, что ему нужно и от кого, и берёт другую задачу.
- **Запреты:** не отключать тесты и линт ради зелёного CI; не коммитить секреты; не добавлять зависимости без указания причины в PR; не делать «временных» клиентских решений исхода боя в онлайне.

## 6. Определение «готово» (для любой задачи)

- [ ] критерии приёмки карточки выполнены;
- [ ] тесты написаны и проходят; тест детерминизма — для `core`;
- [ ] границы пакетов не нарушены (линт);
- [ ] для сети/сервера/аккаунтов — ревью агента безопасности;
- [ ] производительность не просела (смоук FPS) — для рендера и UI;
- [ ] документация обновлена, если менялся контракт или правило игры.
