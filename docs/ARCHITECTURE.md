# Hamsters Life — стек и архитектура

## 1. Требования, из которых выбран стек

1. Браузер на Chromium, 60 FPS (цель — 120 на мощных ПК) при 60 планетах, 500+ отрядах в полёте и тысячах частиц.
2. Красивая 2D-графика: свечения, шейдерные туманности, нормали, частицы, плавная анимация.
3. Мультиплеер в реальном времени с сервером как единственным источником истины.
4. Один и тот же код правил на клиенте (одиночная игра, предпросмотр, повторы) и на сервере (сетевые матчи, проверка карт генератора).
5. Логика отделена от отрисовки и тестируется без окна.

## 2. Выбранный стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | **TypeScript** (strict) везде | общий код клиента и сервера, типы для протокола |
| Сборка | **Vite** + **pnpm workspaces** (монорепозиторий) | быстрая сборка, удобное разделение пакетов |
| Рендер | **PixiJS v8** (WebGPU, откат на WebGL2) | самый быстрый зрелый 2D-движок для веба: батчинг, инстансинг, свои шейдеры, фильтры свечения, частицы; WebGPU в Chromium включён по умолчанию |
| Частицы/эффекты | `@pixi/particle-emitter`-подобный свой эмиттер на `ParticleContainer`, шейдеры GLSL/WGSL | десятки тысяч частиц за один вызов отрисовки |
| Анимация войск | **Spine** (`@esotericsoftware/spine-pixi-v8`) для героев и боссов, покадровые атласы + инстансинг для массовых бойцов | плавные анимации хомяков без просадки FPS |
| Интерфейс меню | **SolidJS** поверх канваса (DOM-слой) | меню, лобби, настройки, профиль — проще в DOM; Solid почти не тратит процессор |
| Анимация UI | CSS + Motion One | лёгкая |
| Звук | **Howler.js** (Web Audio) | спрайты звуков, пространственный звук |
| Симуляция | свой пакет `core` на чистом TS, фиксированный тик 20 Гц, **целочисленная/фиксированная** арифметика | детерминизм, повторы, сервер и клиент считают одинаково |
| Поток симуляции на клиенте | **Web Worker** (одиночная игра, генератор, боты) | главный поток занят только отрисовкой |
| Сервер матчей | **Node.js 22 + Colyseus** (комнаты, подбор, переподключение) на **uWebSockets.js**-транспорте | готовые комнаты и подбор, бинарная сериализация, тот же TS-код правил |
| Протокол | бинарный (MessagePack / Colyseus Schema) поверх WebSocket (WSS) | малый трафик, дельты состояния |
| API аккаунтов | **Fastify** (REST) | быстрый, схемы валидации из коробки |
| БД | **PostgreSQL** + **Drizzle ORM** | аккаунты, рейтинги, трофеи, матчи |
| Кэш/очереди | **Redis** | сессии, подбор, лимиты запросов, присутствие |
| Хранилище повторов | S3-совместимое (MinIO локально) | повторы — сжатые ленты команд |
| Тесты | **Vitest** (core, server), **Playwright** (сквозные, смоук графики) | быстрые headless-тесты правил |
| Качество | ESLint (+ правило границ пакетов), Prettier, `tsc --noEmit` в CI | |
| Развёртывание | Docker Compose (dev), позже Kubernetes/Nomad; CDN для статики | |
| Наблюдаемость | Pino-логи, Prometheus + Grafana, Sentry (клиент и сервер) | |

### Почему не другие варианты

- **Phaser** — удобен, но тяжелее и диктует свою структуру сцен; под нашу схему «headless-ядро + чистый рендер» лишний слой. PixiJS даёт больше контроля над производительностью.
- **Three.js / Babylon.js** — 3D не нужен; для 2D с эффектами избыточны.
- **Unity/Godot WebGL-экспорт** — большой размер загрузки, долгий старт, хуже интеграция с DOM-интерфейсом, нельзя разделить код правил с Node-сервером.
- **Свой WebGPU-рендер** — максимум скорости, но месяцы работы; PixiJS v8 уже использует WebGPU. Вернуться к вопросу можно только при доказанном упоре в рендер.
- **Lockstep вместо авторитарного сервера** — меньше трафика, но любой клиент видит всё состояние и рассинхрон ломает матч; для честного PvP выбираем авторитарный сервер (см. §5).

## 3. Структура монорепозитория

```
hamsters-life/
├─ packages/
│  ├─ core/        # правила игры: состояние, тик, бой, бусты, магия, рода войск. НИКАКИХ импортов DOM/Pixi/Node
│  ├─ content/     # данные: планеты, юниты, заклинания, боссы, баланс (JSON + схемы zod)
│  ├─ levelgen/    # генератор карт по seed + проверка балансом (зависит от core, content)
│  ├─ ai/          # боты и поведение боссов (зависит от core)
│  ├─ protocol/    # типы и кодеки сообщений клиент↔сервер, версия протокола
│  └─ shared-ui/   # общие токены дизайна, иконки (без логики игры)
├─ apps/
│  ├─ client/      # Vite-приложение: render (Pixi), input, ui (Solid), net, audio
│  ├─ game-server/ # Colyseus: комнаты матчей, подбор, запуск core на сервере
│  └─ api/         # Fastify: регистрация, вход, профиль, настройки, трофеи, рейтинг
├─ tools/          # редактор карт (позже), симулятор баланса CLI, генератор ассетов
├─ docs/
└─ infra/          # docker-compose, конфиги, миграции БД
```

**Граница по компиляции, а не по договорённости:** `packages/core`, `levelgen`, `ai` собираются с `lib: ["ES2022"]` без `dom` и без типов Node; ESLint-правило `import/no-restricted-paths` запрещает им импортировать `apps/*`, `pixi.js`, `solid-js`. Если расчёт нельзя протестировать без окна — он в неправильном месте.

## 4. Архитектура клиента

```
           ┌────────────── главный поток ───────────────┐        ┌──── Worker ────┐
 мышь/тач →│ Input → Presenter(команды) ─────────────────┼─ cmds →│ core.Simulation │
           │                         ↑                  │        │ ai, levelgen    │
           │ View: Pixi-сцена  ← Interpolator ← снимки ←┼────────┤ (оффлайн)       │
           │ View: Solid-HUD   ← ViewModel              │        └────────────────┘
           └────────────────────────┬───────────────────┘
                                    │ (онлайн) WSS: команды ↑ / дельты ↓
                                    ▼
                               game-server
```

- **Модель** — `core` (чистое состояние и правила).
- **Презентер** — `GamePresenter`: превращает жесты в команды (`SendFleet`, `ApplyBoost`, `CastSpell`), проверяет доступность (хватает ли семечек, перезарядка), отдаёт ViewModel. Не знает Pixi — общается с видом через интерфейс `IGameView`.
- **Представление** — Pixi-сцена и Solid-HUD, реализующие `IGameView`: только рисуют то, что им дали.
- **Источник состояния** — интерфейс `ISimSource` с двумя реализациями: `LocalWorkerSim` (одиночная игра) и `NetworkSim` (онлайн). Презентер не знает, где идёт игра.
- **Интерполяция**: симуляция 20 Гц, отрисовка 60–144 Гц; позиции отрядов интерполируются между снимками, числа гарнизонов «докручиваются» анимацией.

### Производительность рендера

- Все планеты — один атлас текстур, отряды — `ParticleContainer`/инстансинг (один вызов отрисовки на тип).
- Числа гарнизонов — битмап-шрифт (MSDF), без пересоздания текстур.
- Туманности фона — один полноэкранный шейдер, рендерится в половинном разрешении на «среднем» качестве.
- Пулы объектов, никаких аллокаций в кадре; профилирование через Chrome DevTools Performance и `stats.js` в dev-сборке.
- Автоматическое снижение качества при падении FPS ниже 50 в течение 3 с.
- Цели бюджета: кадр ≤ 8 мс на средней видеокарте, первая загрузка ≤ 5 МБ (gzip), старт до меню ≤ 3 с.

## 5. Сетевая модель

- **Авторитарный сервер.** Матч целиком живёт в комнате `game-server`, где крутится тот же `core.Simulation`.
- **Клиент присылает только намерения**: `{type:"SendFleet", from:[ids], to:id, ratio:50, seq, clientTick}`. Сервер проверяет и применяет на ближайшем тике.
- **Сервер рассылает** дельты состояния 20 раз в секунду (только изменившиеся поля), полный снимок — при входе и переподключении.
- **Отклик управления**: стрелка и «призрак» вылетающего отряда показываются мгновенно (оптимистично), подтверждение приходит через RTT; при отказе — откат с подсказкой.
- **Туман войны (опция режима)** — сервер фильтрует, что отправлять каждому игроку: клиент физически не получает скрытые данные.
- **Повтор** = seed + параметры карты + лента принятых сервером команд с номерами тиков; клиент воспроизводит его в Worker.

## 6. Бэкенд аккаунтов (`apps/api`)

Ресурсы: `/auth` (регистрация, вход, выход, обновление, восстановление), `/me` (профиль, настройки), `/trophies` (список, раскладка комнаты трофеев), `/matches` (история, повторы), `/leaderboard`, `/rooms` (создание частной комнаты → билет на вход в game-server).

Таблицы: `users`, `credentials`, `sessions`, `settings`, `ratings`, `seasons`, `matches`, `match_players`, `trophies`, `user_trophies`, `trophy_room_layout`, `friends`, `audit_log`.

Игровой сервер не ходит в БД на каждый тик: по завершении матча отправляет подписанный результат в `api` (внутренняя сеть), тот обновляет рейтинги и выдаёт трофеи.

## 7. Безопасность онлайн-режима

Подробно — в [SECURITY.md](SECURITY.md). Коротко:
- сервер — единственный источник истины, клиент ничего не решает;
- каждая команда проверяется (владение, количество, перезарядки, частота);
- пароли — Argon2id, сессии — короткий access-токен + ротируемый refresh в httpOnly-cookie;
- только WSS/HTTPS, CSP, ограничение частоты запросов, аудит;
- результаты матчей и трофеи выдаёт только сервер, клиент не может «прислать победу»;
- шифрование памяти: игровые значения в клиенте хранятся замаскированными с контрольной суммой, локальные сохранения — AES-GCM, данные на сервере — шифрование дисков и чувствительных полей.

## 8. Данные и баланс

- Все числа баланса — в `packages/content` (JSON, схемы zod), не в коде. Изменение баланса = правка данных + прогон симулятора баланса.
- `tools/balance-sim` — CLI: гоняет тысячи матчей ботов headless, выдаёт процент побед кланов/родов войск, среднюю длительность.

## 9. Тестирование

| Уровень | Что | Где |
|---|---|---|
| Модульные | бой, производство, бусты, магия, генератор, ИИ | Vitest, `packages/*` |
| Детерминизм | один seed + лента команд → одинаковый хэш состояния на клиенте и сервере | Vitest, CI |
| Свойства | случайные ленты команд: гарнизоны ≥ 0, сумма хомяков сходится | fast-check |
| Протокол | кодеки, отказ на мусорных сообщениях | Vitest |
| Сервер | комнаты, переподключение, проверка команд, нагрузка (k6/Artillery) | Vitest + нагрузочные |
| Сквозные | вход → лобби → матч с ботом → результат → трофей | Playwright (Chromium) |
| Графика | смоук: сцена грузится, FPS ≥ порога в эталонной сцене, скриншот-сравнение | Playwright |
