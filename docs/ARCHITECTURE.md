# Hamsters Life — стек и архитектура

## 1. Требования, из которых выбран стек

1. Браузер на Chromium, 60 FPS (цель — 120 на мощных ПК) при 60 планетах, 500+ отрядах в полёте и тысячах частиц.
2. Красивая 2D-графика: свечения, шейдерные туманности, нормали, частицы, плавная анимация.
3. Мультиплеер в реальном времени с сервером как единственным источником истины.
4. Один и тот же код правил на клиенте (одиночная игра, предпросмотр, повторы) и на сервере (сетевые матчи, проверка карт генератора).
5. Логика отделена от отрисовки и тестируется без окна.

## 2. Выбранный стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | **TypeScript** (strict) везде | общий код клиента и сервера, типы для протокола |
| Сборка | **Vite** + **pnpm workspaces** (монорепозиторий) | быстрая сборка, удобное разделение пакетов |
| Рендер | **PixiJS v8** (WebGPU, откат на WebGL2) | самый быстрый зрелый 2D-движок для веба: батчинг, инстансинг, свои шейдеры, фильтры свечения, частицы; WebGPU в Chromium включён по умолчанию |
| Частицы/эффекты | `@pixi/particle-emitter`-подобный свой эмиттер на `ParticleContainer`, шейдеры GLSL/WGSL | десятки тысяч частиц за один вызов отрисовки |
| Анимация войск | **Spine** (`@esotericsoftware/spine-pixi-v8`) для героев и боссов, покадровые атласы + инстансинг для массовых бойцов | плавные анимации хомяков без просадки FPS |
| Интерфейс меню | **SolidJS** поверх канваса (DOM-слой) | меню, лобби, настройки, профиль — проще в DOM; Solid почти не тратит процессор |
| Анимация UI | CSS + Motion One | лёгкая |
| Звук | **Howler.js** (Web Audio) | спрайты звуков, пространственный звук |
| Симуляция | свой пакет `core` на чистом TS, фиксированный тик 20 Гц, **целочисленная/фиксированная** арифметика | детерминизм, повторы, сервер и клиент считают одинаково |
| Поток симуляции на клиенте | **Web Worker** (одиночная игра, генератор, боты) | главный поток занят только отрисовкой |
| Сервер матчей | **Node.js 22 + Colyseus** (комнаты, подбор, переподключение) на **uWebSockets.js**-транспорте | готовые комнаты и подбор, бинарная сериализация, тот же TS-код правил |
| Протокол | бинарный (MessagePack / Colyseus Schema) поверх WebSocket (WSS) | малый трафик, дельты состояния |
| API аккаунтов | **Fastify** (REST) | быстрый, схемы валидации из коробки |
| БД | **PostgreSQL** + **Drizzle ORM** | аккаунты, рейтинги, трофеи, матчи |
| Кэш/очереди | **Redis** | сессии, подбор, лимиты запросов, присутствие |
| Хранилище повторов | S3-совместимое (MinIO локально) | повторы — сжатые ленты команд |
| Тесты | **Vitest** (core, server), **Playwright** (сквозные, смоук графики) | быстрые headless-тесты правил |
| Качество | ESLint (+ правило границ пакетов), Prettier, `tsc --noEmit` в CI | |
| Развёртывание | Docker Compose (dev), позже Kubernetes/Nomad; CDN для статики | |
| Наблюдаемость | Pino-логи, Prometheus + Grafana, Sentry (клиент и сервер) | |

### Почему не другие варианты

- **Phaser** — удобен, но тяжелее и диктует свою структуру сцен; под нашу схему «headless-ядро + чистый рендер» лишний слой. PixiJS даёт больше контроля над производительностью.
- **Three.js / Babylon.js** — 3D не нужен; для 2D с эффектами избыточны.
- **Unity/Godot WebGL-экспорт** — большой размер загрузки, долгий старт, хуже интеграция с DOM-интерфейсом, нельзя разделить код правил с Node-сервером.
- **Свой WebGPU-рендер** — максимум скорости, но месяцы работы; PixiJS v8 уже использует WebGPU. Вернуться к вопросу можно только при доказанном упоре в рендер.
- **Lockstep вместо авторитарного сервера** — меньше трафика, но любой клиент видит всё состояние и рассинхрон ломает матч; для честного PvP выбираем авторитарный сервер (см. §5).

## 3. Структура монорепозитория

```
hamsters-life/
├─ packages/
│  ├─ core/        # правила игры: состояние, тик, бой, бусты, магия, рода войск. НИКАКИХ импортов DOM/Pixi/Node
│  ├─ content/     # данные: планеты, юниты, заклинания, боссы, баланс (JSON + схемы zod)
│  ├─ levelgen/    # генератор карт по seed + проверка балансом (зависит от core, content)
│  ├─ ai/          # боты и поведение боссов (зависит от core)
│  ├─ protocol/    # типы и кодеки сообщений клиент↔сервер, версия протокола
│  └─ shared-ui/   # общие токены дизайна, иконки (без логики игры)
├─ apps/
│  ├─ client/      # Vite-приложение: render (Pixi), input, ui (Solid), net, audio
│  ├─ game-server/ # Colyseus: комнаты матчей, подбор, запуск core на сервере
│  └─ api/         # Fastify: регистрация, вход, профиль, настройки, трофеи, рейтинг
├─ tools/          # редактор карт (позже), симулятор баланса CLI, генератор ассетов
├─ docs/
└─ infra/          # docker-compose, конфиги, миграции БД
```

**Граница по компиляции, а не по договорённости:** `packages/core`, `levelgen`, `ai` собираются с `lib: ["ES2022"]` без `dom` и без типов Node; ESLint-правило `import/no-restricted-paths` запрещает им импортировать `apps/*`, `pixi.js`, `solid-js`. Если расчёт нельзя протестировать без окна — он в неправильном месте.

## 4. Архитектура клиента

```
           ┌────────────── главный поток ───────────────┐        ┌──── Worker ────┐
 мышь/тач →│ Input → Presenter(команды) ─────────────────┼─ cmds →│ core.Simulation │
           │                         ↑                  │        │ ai, levelgen    │
           │ View: Pixi-сцена  ← Interpolator ← снимки ←┼────────┤ (оффлайн)       │
           │ View: Solid-HUD   ← ViewModel              │        └────────────────┘
           └────────────────────────┬───────────────────┘
                                    │ (онлайн) WSS: команды ↑ / дельты ↓
                                    ▼
                               game-server
```

- **Модель** — `core` (чистое состояние и правила).
- **Презентер** — `GamePresenter`: превращает жесты в команды (`SendFleet`, `ApplyBoost`, `CastSpell`), проверяет доступность (хватает ли семечек, перезарядка), отдаёт ViewModel. Не знает Pixi — общается с видом через интерфейс `IGameView`.
- **Представление** — Pixi-сцена и Solid-HUD, реализующие `IGameView`: только рисуют то, что им дали.
- **Источник состояния** — интерфейс `ISimSource` с двумя реализациями: `LocalWorkerSim` (одиночная игра) и `NetworkSim` (онлайн). Презентер не знает, где идёт игра.
- **Интерполяция**: симуляция 20 Гц, отрисовка 60–144 Гц; позиции отрядов интерполируются между снимками, числа гарнизонов «докручиваются» анимацией.

### Производительность рендера

- Все планеты — один атлас текстур, отряды — `ParticleContainer`/инстансинг (один вызов отрисовки на тип).
- Числа гарнизонов — битмап-шрифт (MSDF), без пересоздания текстур.
- Туманности фона — один полноэкранный шейдер, рендерится в половинном разрешении на «среднем» качестве.
- Пулы объектов, никаких аллокаций в кадре; профилирование через Chrome DevTools Performance и `stats.js` в dev-сборке.
- Автоматическое снижение качества при падении FPS ниже 50 в течение 3 с.
- Цели бюджета: кадр ≤ 8 мс на средней видеокарте, первая загрузка ≤ 5 МБ (gzip), старт до меню ≤ 3 с.

## 5. Сетевая модель

- **Авторитарный сервер.** Матч целиком живёт в комнате `game-server`, где крутится тот же `core.Simulation`.
- **Клиент присылает только намерения**: `{type:"SendFleet", from:[ids], to:id, ratio:50, seq, clientTick}`. Сервер проверяет и применяет на ближайшем тике.
- **Сервер рассылает** дельты состояния 20 раз в секунду (только изменившиеся поля), полный снимок — при входе и переподключении.
- **Отклик управления**: стрелка и «призрак» вылетающего отряда показываются мгновенно (оптимистично), подтверждение приходит через RTT; при отказе — откат с подсказкой.
- **Туман войны (опция режима)** — сервер фильтрует, что отправлять каждому игроку: клиент физически не получает скрытые данные.
- **Повтор** = seed + параметры карты + лента принятых сервером команд с номерами тиков; клиент воспроизводит его в Worker.

## 6. Бэкенд аккаунтов (`apps/api`)

Ресурсы: `/auth` (регистрация, вход, выход, обновление, восстановление), `/me` (профиль, настройки), `/trophies` (список, раскладка комнаты трофеев), `/matches` (история, повторы), `/leaderboard`, `/rooms` (создание частной комнаты → билет на вход в game-server).

Таблицы: `users`, `credentials`, `sessions`, `settings`, `ratings`, `seasons`, `matches`, `match_players`, `trophies`, `user_trophies`, `trophy_room_layout`, `friends`, `audit_log`.

Игровой сервер не ходит в БД на каждый тик: по завершении матча отправляет подписанный результат в `api` (внутренняя сеть), тот обновляет рейтинги и выдаёт трофеи.

## 7. Безопасность онлайн-режима

Подробно — в [SECURITY.md](SECURITY.md). Коротко:
- сервер — единственный источник истины, клиент ничего не решает;
- каждая команда проверяется (владение, количество, перезарядки, частота);
- пароли — Argon2id, сессии — короткий access-токен + ротируемый refresh в httpOnly-cookie;
- только WSS/HTTPS, CSP, ограничение частоты запросов, аудит;
- результаты матчей и трофеи выдаёт только сервер, клиент не может «прислать победу»;
- шифрование памяти: игровые значения в клиенте хранятся замаскированными с контрольной суммой, локальные сохранения — AES-GCM, данные на сервере — шифрование дисков и чувствительных полей.

## 8. Данные и баланс

- Все числа баланса — в `packages/content` (JSON, схемы zod), не в коде. Изменение баланса = правка данных + прогон симулятора баланса.
- `tools/balance-sim` — CLI: гоняет тысячи матчей ботов headless, выдаёт процент побед кланов/родов войск, среднюю длительность.

## 9. Тестирование

| Уровень | Что | Где |
|---|---|---|
| Модульные | бой, производство, бусты, магия, генератор, ИИ | Vitest, `packages/*` |
| Детерминизм | один seed + лента команд → одинаковый хэш состояния на клиенте и сервере | Vitest, CI |
| Свойства | случайные ленты команд: гарнизоны ≥ 0, сумма хомяков сходится | fast-check |
| Протокол | кодеки, отказ на мусорных сообщениях | Vitest |
| Сервер | комнаты, переподключение, проверка команд, нагрузка (k6/Artillery) | Vitest + нагрузочные |
| Сквозные | вход → лобби → матч с ботом → результат → трофей | Playwright (Chromium) |
| Графика | смоук: сцена грузится, FPS ≥ порога в эталонной сцене, скриншот-сравнение | Playwright |

## 10. Детерминизм и целочисленная арифметика

Требование: один seed + одна лента команд → одинаковое состояние и одинаковый хэш на клиенте, сервере и в тестах.

1. **В `packages/core` нет чисел с плавающей точкой.** Войска и семечки — целые milli-единицы (1 хомяк = 1000 mH), проценты — permille (1.0 = 1000). Расстояние — целочисленный корень, а не `Math.sqrt`.
2. **Деление только нацело.** Округление вниз (`mulPermille`, `resolveCapture`), время полёта — вверх (`ceilDiv`). Обратный пересчёт гарнизона после обороны — вниз.
3. **Тик 20 Гц (50 мс).** Порядок внутри тика зафиксирован: обучение в казармах → производство и поток маршрутов (с выпуском накопленных отрядов) → семечки → продвижение флотов → разрешение прибытий → выбывание игроков. Менять порядок — значит повышать `rulesVersion`.
4. **Одновременные прибытия** разрешаются в порядке возрастания id флота. id монотонно растёт при отправке, поэтому порядок не зависит от машины и кадров. Это документированный tie-break (`IDEA.md` §3.4.1).
5. **Числа контента обязаны делиться на 20** там, где они заданы «в секунду»: производство превращается в «за тик» делением нацело. Проверяется тестом контента.
6. **Хэш состояния** (`hashState`, FNV-1a по полям в порядке массивов) — единственный способ сравнивать партии. `rulesVersion` входит в состояние и в хэш.
7. **Повтор матча** хранит `rulesVersion`, `contentVersion`, seed и ленту команд с номерами тиков. Повтор, снятый на другой версии правил, не воспроизводится — это ожидаемо и показывается игроку, а не «чинится» подгонкой.
8. **`ProtectedInt` — только на границе клиента.** Маскируются копии для отображения и сохранений; сам `core` считает на открытых целых, иначе ломаются хэш и совпадение с сервером (см. SECURITY.md §6.1).

## 11. Решения (журнал)

Сюда попадает то, что меняет правило или контракт и должно быть понятно агенту без общего контекста. Формат: дата — решение — причина. Детали — в коде и тестах, здесь — «почему».

- **2026-11-15 — целочисленное ядро** (milli-единицы, permille, целочисленный корень) вместо floats. Причина: детерминизм и совпадение клиента с сервером.
- **2026-11-15 — одновременные прибытия** разрешаются турниром по id флота; свои сливаются, чужие бьются, равные уничтожаются. Причина: простая и воспроизводимая модель при трёх и более участниках.
- **2026-11-15 — гарнизон может стать 0** после успешной обороны. Причина: формула §3.4 без искусственных исключений; планета удержана, но беззащитна.
- **2026-11-15 — при захвате сбрасываются бусты** прежнего владельца. Причина: буст — свойство владельца, а не здания.
- **2026-11-15 — отправка с нескольких планет даёт отдельные флоты.** Причина: у планет разное расстояние, единый флот пришлось бы считать по средней скорости — нечестно и неочевидно.
- **2026-11-15 — `nodeLinker: hoisted`.** Причина: на Windows-машинах Node не разворачивает junction'ы pnpm, изолированная раскладка ломает `tsc` и `vitest` (DEVELOPMENT.md §3.1).
- **2026-11-15 — Vitest с `--pool=threads`.** Причина: песочница агента запрещает `spawn` с перехватом вывода (DEVELOPMENT.md §3.2).
- **2026-11-15 — пакеты собираются `tsc --noEmit`** до появления серверного приложения; клиент собирает Vite. Причина: не плодить двойную сборку на этапе 0; вернуться к emit, когда появится `apps/game-server`.
- **2026-11-15 — ESLint линтует только служебные JS/MJS.** `typescript-eslint` 8.72 не поддерживает TypeScript 7 (нативный компилятор) и падает при загрузке парсера. Границы пакетов держатся надёжнее: `tsconfig` пакета без DOM и Node-типов + `tools/check-boundaries.mjs`. Вернуться к TS-линту, когда парсер поддержит TS 7; до тех пор `pnpm lint` — про `tools/` и конфиги.
- **2026-11-15 — арт и звук этапа 1 процедурные.** Планеты, капсулы, стрелки, частицы и звуки делаются кодом (Pixi `Graphics`, WebAudio-осцилляторы и шум), без внешних ассетов. Причина: решение человека, нулевая загрузка, нет лицензионных вопросов, легко менять цвета под кланы. Финальный арт — этап 10.
- **2026-11-15 — изоляция через порты.** Ядро объявляет интерфейсы `ContentProvider`, `SimSource`, `Scheduler`, `Bot`; пакет `content` реализует `ContentProvider`, клиент — `SimSource` и `Scheduler`, пакет `ai` — `Bot`. Партия инкапсулирована в классе `Simulation` (баланс и карта приходят в конструктор). Причина: любой слой подменяется в тестах без окна и без сети; «временных» зависимостей от Pixi/DOM в правилах не появляется.
- **2026-11-15 — бусты хранятся записью по видам, тик собран из систем.** `Planet.boosts` — `Record<BoostKind, Tick>`, хэш и сброс идут по `BOOST_KINDS`; порядок правил тика задаёт массив `TICK_SYSTEMS` в `systems.ts`. Причина: добавление буста или правила — это одна запись в списке, а не правка трёх таймеров и монолитной функции; поведение закреплено тестами.
- **2026-11-15 — повтор матча = seed + версии + лента команд.** Состояние не сохраняется. Для сгенерированных карт имя `duel-<seed>`, а алгоритм генератора считается частью версии правил: изменил генератор — подними `rulesVersion`, иначе старые повторы честно не воспроизведутся. Причина: повтор весит килобайты и не расходится с кодом; несовместимость показывается, а не маскируется.
- **2026-11-15 — Worker отвечает оптимистично.** `WorkerSimSource.sendCommand` сразу возвращает `ok`, а отказ приходит сообщением в `onRejected`. Причина: команда уже показана игроку (стрелка, звук), ждать RTT бессмысленно; проверка остаётся в ядре и в Worker, «доверия» клиенту не появляется. Worker включается флагом `?worker=1`.
- **2026-11-15 — движение переведено на постоянные маршруты (rulesVersion 2).** Стрелка живёт, пока её не отрежут, и непрерывно тянет производство: ниже вместимости — долю `min(100%, Σвесов)`, на вместимости — всё. Доли нормализуются по весам, накопление идёт в milli-единицах, отряд выпускается на 1 хомяка. Причина: игрок не должен «перебрасывать заново» каждые несколько секунд, а поток должен честно делиться между стрелками; старые повторы (версия 1) несовместимы — это показывается, а не маскируется.
- **2026-11-15 — скорость игры — множитель частоты тиков**, а не растягивание правил: 0.2…2. Бот использует тот же множитель для интервала решений, поэтому при замедлении не получает преимущества. Причина: «не успеваю за ботом» лечится темпом, а не ослаблением ИИ.
- **2026-11-15 — этап 2 переводит гарнизон на `TroopStack` поэтапно.** Сначала данные родов войск и кланов в `content` и утилиты состава в ядре (не влияют на игру), затем планеты/флоты начинают хранить состав с сохранением суммы, затем включается фазовый бой. Причина: играбельная сборка этапа 1 не должна ломаться на середине миграции; каждый шаг проверяется тестами, а `rulesVersion` поднимается, когда меняются правила, а не структура хранения.
- **2026-11-15 — миграция на состав завершена (rulesVersion 3).** `Planet.troops`, `Fleet.troops`, `Route.pending` — это `TroopStack`; численность всегда `troopTotal`, поэтому правила по сумме не изменились, но старые повторы версии 2 несовместимы. Производство даёт базовых бойцов (мечников), поток маршрута тоже; излишек и подкрепление сохраняют пропорции состава; захват пересчитывает состав победителя на точное число (`resizeTroops`, крупнейший остаток). Причина точности: сумма гарнизона остаётся целой и проверяемой, а состав не «размывается» округлением по каждому роду.
- **2026-11-15 — захват переведён на фазовый бой (rulesVersion 4).** Три фазы (дальний обмен → сближение → ближний бой), силы берутся из `troops.json`, потери — доля от состава с учётом наступательной мощи против защитной. Старая формула «атакующие минус защита» удалена из кода, чтобы не было двух правд. Причина: рода войск должны влиять на исход, а не быть косметикой; числа боя (`combat` в балансе) вынесены в данные для будущего симулятора баланса.

## 12. Как расширять (рецепты)

Каждая задача ниже — на 10–30 строк, без переписывания соседних слоёв. Если рецепт не подходит, значит изменение меняет контракт: сначала раздел «Решения», потом код.

### Новый буст

1. В `packages/core/src/types.ts` добавить вид в конец `BOOST_KINDS`.
2. В `packages/content/src/schema.ts` — поле в `boosts`, в `balance.json` — числа (стоимость, длительность, перезарядка, множитель).
3. Применение эффекта — в `modifiers.ts` (если это множитель) или отдельной системой тика (если эффект иной).
4. `Planet.boosts`, хэш и сброс при захвате уже идут по `BOOST_KINDS` — править их не нужно.
5. Кнопка в HUD строится перебором `BOOST_KINDS` и появится сама; добавить только подпись и иконку в `ui/boostIcon`.
6. Тесты: действует, истекает, сбрасывается при захвате, входит в хэш.

### Новый тип команды

1. Вариант в `Command` и код отказа в `CommandErrorCode` (`types.ts`).
2. Ветка в `applyCommand` (`commands.ts`) — компилятор напомнит через `assertNever`.
3. Общий для клиента и сервера тест: команда применяется и отклоняется по каждому коду.
4. Метод презентера, который её отправляет (`GamePresenter`), и элемент интерфейса.
5. На этапе 8 — схема в `packages/protocol`.

### Новая система тика

1. Функция `TickSystem` в `packages/core/src/systems.ts` — «состояние + контекст → изменение».
2. Вставить в `TICK_SYSTEMS`; порядок записать в `IDEA.md` §3.4.1 и `ARCHITECTURE.md` §10.
3. Тест на изолированный эффект + прогон теста детерминизма (хэш).
4. Если меняются правила — поднять `rulesVersion` в `balance.json`.

### Новая карта или режим

1. JSON в `packages/content/src/data/`, схема `mapDefinitionSchema` (строгая).
2. Зарегистрировать в `MAPS` (`content/src/index.ts`); для PvP — тест симметрии.
3. Режим — это набор систем тика и условий победы; отдельный класс режима появится на этапе 4, пока условие одно.

### Новый экран или слой клиента

1. Расширить интерфейс вида (`apps/client/src/presenter/viewModel.ts`), если нужны новые данные.
2. Слой Pixi — отдельный класс в `render/`, подключается в `GameScene`; ничего не знает о правилах.
3. Логика экрана — в презентере, без Pixi и DOM: проверяется тестом без окна.
4. Элементы HUD — Solid-компоненты в `ui/`, данные приходят из `BoardView`.

### Когда придётся менять модель (планируем заранее)

- **Рода войск (этап 2):** `garrison: MilliUnits` станет составом (`TroopStack`), а бой — фазовым. Точка входа одна — `combat.ts`; тип `Planet` меняется вместе с хэшем и экраном состава. До этапа 2 не «готовим поля заранее».
- **Мана и заклинания (этап 5):** новый ресурс игрока и команда каста; добавляются теми же рецептами.
- **Сетевой режим (этап 8):** `SimSource` уже отделён — появляется `NetworkSimSource`, презентер не меняется.
