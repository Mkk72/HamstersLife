# Hamsters Life — безопасность онлайн-режима

Цель: игрок не может получить преимущество модификацией клиента, подделкой сетевых сообщений или чужим аккаунтом; сервис выдерживает перебор паролей и наводнение запросами.

## 1. Модель угроз

| Угроза | Пример | Защита |
|---|---|---|
| Модифицированный клиент | «отправить 1000 хомяков с планеты, где их 10», ускорить производство | авторитарный сервер, проверка команд (§2) |
| Подделка сообщений | ручные WebSocket-пакеты, повтор старых | схема-валидация, `seq`, привязка к сессии |
| Ботоводство / макросы | идеальный ИИ вместо игрока | лимиты частоты, статистический анализ, жалобы (§4) |
| Чтение скрытой информации | туман войны, колода заклинаний врага | сервер не отправляет скрытые данные (§2.4) |
| Подделка результата | «я выиграл», «дайте трофей» | результаты и трофеи только с сервера, подпись (§3.4) |
| Кража аккаунта | перебор, утечка пароля, XSS-кража токена | Argon2id, лимиты, httpOnly-cookie, CSP, 2FA (§3) |
| Сговор / буст рейтинга | договорные матчи, мультиаккаунты | анализ пар игроков, ограничения по устройству/IP (§4) |
| DoS | флуд подключений и команд | лимиты на шлюзе, Redis-лимитеры, отключение нарушителей (§5) |
| Уязвимые зависимости | цепочка поставки npm | lock-файл, `pnpm audit`, Renovate, проверка в CI (§6) |

## 2. Античит на игровом сервере

### 2.1 Сервер — источник истины
Вся симуляция (производство, полёты, бой, бусты, магия, боссы) выполняется только на `game-server`. Клиент присылает намерения, а состояние получает от сервера. Числа в клиенте — отображение, их правка ничего не меняет.

### 2.2 Проверка каждой команды
Перед применением команды сервер проверяет:
- игрок участвует в матче и не выбыл;
- все планеты-источники принадлежат ему, цель существует;
- доля отправки из разрешённого набора (25/50/75/100), отправляется не больше, чем есть;
- буст/заклинание открыто в этом режиме, хватает семечек/маны, нет перезарядки, цель в радиусе мага;
- `seq` строго растёт (защита от повтора), `clientTick` в допустимом окне;
- частота: не более N команд в секунду (с запасом для быстрых игроков, например 15/с), всплеск — через token bucket.

Нарушения не применяются; счётчик нарушений растёт, при превышении — предупреждение, затем отключение и пометка матча для проверки.

### 2.3 Валидация протокола
- Каждое сообщение декодируется по строгой схеме (`packages/protocol`), лишние поля и неверные типы → отказ.
- Максимальный размер сообщения, запрет неизвестных типов.
- Версия протокола проверяется при подключении; старый клиент получает «обновите страницу».

### 2.4 Минимум информации клиенту
- В режимах с туманом войны сервер фильтрует дельты для каждого игрока (видимость по радиусам планет).
- Колоды заклинаний и выбор кузниц противника не передаются до применения.
- Seed карты в рейтинговом матче не раскрывается до конца (иначе можно заранее просчитать карту).

### 2.5 Вход в матч
- Билет входа выдаёт `api`: короткоживущий (60 с) подписанный токен с `userId`, `matchId`, слотом. Game-server проверяет подпись — без похода в БД.
- Одна сессия на матч: повторное подключение вытесняет старое.

## 3. Аккаунты

### 3.1 Пароли
- Хэш **Argon2id** (память ≥ 64 МБ, параметры по рекомендации OWASP), уникальная соль.
- Минимум 10 символов, проверка по списку утёкших паролей (k-анонимный запрос к Have I Been Pwned или локальная база).
- Подтверждение почты обязательно для рейтинговых игр.

### 3.2 Сессии
- Access-токен 15 минут (в памяти клиента), refresh-токен 30 дней в cookie `HttpOnly; Secure; SameSite=Strict`.
- Ротация refresh при каждом использовании; повторное использование старого → отзыв всей цепочки (признак кражи).
- Список активных сессий в настройках, «выйти везде».

### 3.3 Защита входа
- Лимит попыток входа по аккаунту и по IP (Redis), прогрессивная задержка; после серии неудач — проверка «я не робот» (Cloudflare Turnstile / hCaptcha).
- Одинаковый ответ на «нет такого пользователя» и «неверный пароль».
- Сброс пароля — одноразовая ссылка на 30 минут, после сброса отзываются все сессии.
- Опциональная 2FA (TOTP), обязательная для модераторов.
- Уведомление на почту о входе с нового устройства.

### 3.4 Результаты, рейтинг, трофеи
- Только game-server завершает матч и отправляет результат в `api` по внутренней сети с подписью (HMAC/mTLS). Публичного метода «сообщить результат» нет.
- Трофеи выдаются сервером по правилам из `content`; клиент может только расставлять уже полученные трофеи в комнате (раскладка валидируется: только свои трофеи, лимиты полок).

## 4. Честная игра и модерация
- Повтор каждого рейтингового матча хранится — по нему можно проверить жалобу.
- Сигналы ботоводства: нечеловечески ровные интервалы команд, реакция быстрее 100 мс серийно, игра 24/7. Сигнал → ручная проверка, не автоматический бан.
- Сговор: частые матчи одних и тех же пар с перекосом результата, мультиаккаунты с одного устройства — рейтинговые очки замораживаются до проверки.
- Жалобы из интерфейса, журнал модерации, апелляции.

## 5. Сеть и инфраструктура
- Только HTTPS/WSS (TLS 1.2+), HSTS.
- Заголовки: строгий **CSP** (без `unsafe-eval`, скрипты только со своего домена), `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors 'none'`.
- CORS — только свой домен; CSRF закрыт `SameSite=Strict` и проверкой `Origin`.
- Ники и чат — экранирование при выводе (Solid экранирует по умолчанию; `innerHTML` запрещён правилом ESLint), фильтр нецензурного.
- Шлюз (Cloudflare/NGINX): лимит подключений на IP, защита от флуда, скрытие адресов серверов.
- Секреты — в переменных окружения/хранилище секретов, не в репозитории; разные ключи для dev/staging/prod.
- БД — параметризованные запросы (Drizzle), минимальные права учётных записей сервисов, резервные копии, шифрование дисков.
- Журнал безопасности: входы, смена пароля/почты, отключения за нарушения, действия модераторов.

## 6. Шифрование памяти и данных

Требование: значения игры не лежат в памяти и хранилищах открытым текстом.

### 6.1 Память клиента (против Cheat Engine, правки через DevTools)
- Важные числа (гарнизоны, семечки, мана, перезарядки, таймеры) в клиентской симуляции хранятся в обёртке `ProtectedInt`/`ProtectedState`: значение XOR-ится с ключом сессии, ключ периодически (раз в несколько секунд) меняется с перешифровкой, рядом хранится контрольная сумма. Несовпадение суммы = признак вмешательства → оффлайн-матч помечается, рекорд не засчитывается, в онлайне — отправка сигнала на сервер.
- Типизированные массивы состояния в Worker не экспортируются наружу; в главный поток уходят только снимки для отрисовки.
- Production-сборка: минификация, без source maps в открытом доступе (карты — только в Sentry), `console`/отладочные хуки вырезаются.
- Для онлайна это второй рубеж: даже расшифровав память, игрок меняет только отображение — решения принимает сервер (§2.1).

### 6.2 Локальное хранилище
- Сохранения оффлайн-кампании, настройки гостя и кэш повторов в IndexedDB шифруются **AES-GCM** (Web Crypto API); ключ — неэкспортируемый `CryptoKey`, для вошедшего игрока — производный от ключа, выданного сервером. GCM-тег защищает от правки сохранения руками.
- Токены доступа в `localStorage` не хранятся вообще (§3.2).
- Прогресс, влияющий на рейтинг и трофеи, всегда хранится и проверяется на сервере; локальная копия — только кэш.

### 6.3 Трафик
- WSS/HTTPS с TLS 1.3 (§5). Внутри — бинарный протокол; сообщения матча дополнительно подписываются ключом сессии матча (HMAC), чтобы подмена внутри скомпрометированного прокси была видна.

### 6.4 Сервер и база
- Диски БД, Redis и хранилища повторов шифруются (encryption at rest), резервные копии — тоже, ключи — в KMS/Vault.
- Чувствительные поля (почта, секрет 2FA, IP в журналах) дополнительно шифруются на уровне приложения (AES-GCM, конверт с ключом из KMS); для поиска по почте — отдельный HMAC-индекс.
- Пароли не шифруются, а хэшируются (Argon2id, §3.1).
- Межсервисный трафик (api ↔ game-server ↔ БД) — mTLS.

## 7. Процесс разработки
- `pnpm audit` и Renovate в CI, lock-файл обязателен, новые зависимости — через ревью.
- Тесты безопасности в CI: мусорные/злые сообщения протокола, команды с чужими планетами, превышение частоты, подделка билета, повторное использование refresh-токена.
- Перед открытым запуском — внешний аудит / bug bounty, чек-лист OWASP ASVS уровня 2.
- Обфускация клиента не считается защитой: клиент изначально считается враждебным.
